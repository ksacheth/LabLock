1 · Collapse the submit loop into a Grading module

Strong in-process

apps/api/src/routes/student.routes.ts · submit (450–641) + run (304–448) → lib/scoring.ts · lib/submissions.ts · execution/judge.ts

Before — 190-line handler

submit handler

load questions
for each question ↓
load latest submission
load test cases
→ judge()
→ calculateWeightedQuestionScore()
→ upsertStudentSubmissionRecord()
PENDING / SYSTEM_ERROR branch
push breakdown row, round
sum + complete attempt (write)

run handler repeats judge → upsert → shape response.

After — deep Grading module

gradeAttempt(exam, attempt, deps)

→ GradeReport { totalScore, breakdown }

gradeQuestion()  (internal)
judge · score · persist  (injected)
PENDING / SYSTEM_ERROR rows
run handler → gradeQuestion()

Handlers load I/O, call one interface, write the response.

Problem. The submit handler is a Brain Method — judge, score, persist and the SYSTEM_ERROR/PENDING policy are interleaved in one loop; run duplicates half of it.

Solution. A gradeAttempt module owning the per-question grading orchestration; judge and persistence pass in as dependencies.

  • locality: SYSTEM_ERROR quarantine lives in one module
  • leverage: run and submit share gradeQuestion
  • interface is the test surface — no Express, no Prisma
  • interface shrinks; handler absorbs only I/O
ADR-0004 note. Complements it — ExamSession stays read-only; the attempt-completion write moves into a distinct grading module, not into openSession.

Problem. The indent/outdent offset math and the syntax highlighter are already pure, but buried in a 1830-line component with no seam and no tests — the exact code where bugs hide.

Solution. Move them to an editor-text module — same functions, one interface, isolated from React.

  • test surface: offset math, no DOM
  • locality: highlighter grammars in one place
  • AI-navigability: room file drops ~360 lines
  • no behaviour change — pure lift

4 · A decision core for the strike / disqualify policy

Worth exploring in-process

apps/api/src/routes/student.routes.ts · violations (201–302)

Before — policy interleaved with I/O in the handler

flowchart LR
  H[violations handler] --> R[rate-limit query 2s]
  H --> W[create proctoringLog]
  H --> C[count TAB+FULLSCREEN]
  C --> D{count ≥ 3?}
  D -->|leak| U[update attempt: DISQUALIFIED]
  H --> L[logApiEvent]
  classDef leak stroke:#dc2626,stroke-width:2px,fill:#fef2f2;
  class D,U leak

After — pure decision, adapter does the writes

flowchart LR
  H[violations handler] -->|snapshot| E["evaluateViolation(type, priorStrikes, now)"]
  E --> O["Outcome { record?, strikes, disqualify }"]
  O --> H
  H --> W[create log / disqualify]
  style E fill:#0f172a,color:#fff,stroke:#0f172a
  style O fill:#0f172a,color:#fff,stroke:#0f172a

Problem. Rate-limit window, strike-counting, and the "3 strikes → disqualify" rule are inlined with Prisma calls — the policy has no test surface and echoes the client's own strike text.

Solution. An evaluateViolation core returning a typed Outcome — the same discriminated-result shape as Decision and Refusal.

  • disqualification policy becomes a table
  • interface is the test surface
  • consistent with authorize / evaluateSession
  • strike threshold defined once
ADR-0004 note. Same shape as Candidate 1 — the disqualify write stays in the handler/adapter; only the decision moves behind the seam.
